# ADR-015：认领未决时等待窗口结束，不再「pending 即胜出」

| 项目 | 值 |
|---|---|
| 日期 | 2026-10-27 11:30（Asia/Shanghai） |
| 状态 | 已决定，待实现 + V21 复测 |
| 修订 | ADR-011 §「decide 时：claim 仍在途 → 按胜出处理（降级）」 |
| 关联 | R2、V21、F7 |

## 1. 问题

V21 真机：两个标签（同窗口，前台 + 后台）同一次完成，**两个标签都入队**，前台出现两条浮层（第二行会话名不同——后台标签缺工区快照，回退「未分组」）。日志证据：

```text
status:false   at=…468
decide         at≈…489   (+21 ms)  → claim-pending-at-decide
onEnqueued     at=…489   hidden:true    // 后台标签也入队
status:false   at=…468   （另一标签同一事件）
```

原因：`decide` 在观察窗结束时立即运行（后台走 `queueMicrotask`，约 +20 ms），而认领窗 `claimWindowMs=80 ms`。**判定永远早于认领结果**，`claim` 恒为 `pending`；ADR-011 又规定 pending 按胜出处理，于是所有标签都赢。

这是实现与契约共同造成的结构性缺陷，不是时序偶发。

## 2. 决定

`decide` 遇到 `claim === 'pending'` 时**不再直接胜出**，而是：

1. 计算剩余窗口 `remaining = claimStartedAt + claimWindowMs - now`；
2. 若 `remaining > 0`，延迟 `remaining`（≤80 ms）后**重新判定**；期间状态保持 `settling`，并沿用 `generation` 守卫；
3. 延迟结束：
   - `won` → 正常入队；
   - `lost` → 丢弃，不入队、不通知、不更新冷却/发射计数；
   - 仍 `pending`（例如无 `BroadcastChannel`、通道异常）→ 按胜出处理（真正的降级路径，保留但不再是常态）。

**约束**：新增延迟不得超过 `claimWindowMs`（默认 80 ms），总时延预算仍满足 P95 ≤ 500 ms；不得为等待认领而推迟通知超过 80 ms。

## 3. 理由

- 让「认领窗」真正起到窗口作用，而不是装饰；
- 语义上「不确定就双弹」违反 F7「不重复」；宁可晚 80 ms，也不重复；
- 与时延预算兼容：250 ms 观察窗 + 80 ms 认领（并行于解析）+ 渲染，仍 < 500 ms。

## 4. 代价

- 双标签场景下提示可能晚 ≤80 ms；
- 复杂化 `decide`：需要一次可取消的延迟与二次判定，必须复用 `generation`/state 守卫，避免重复入队。

## 5. 被否决

| 方案 | 理由 |
|---|---|
| 维持 pending 即胜出 | V21 必然失败，F7 不成立 |
| 把认领窗降到 0–10 ms | 网络/事件循环抖动下仍不可靠；只是把窗口藏起来 |
| 取消认领、改用常驻 leader | 引入存储与选举复杂度，ADR-011 已否决 |
| 只在双标签时启用等待 | 无法可靠判定「是否双标签」，且行为不一致 |

## 6. 测试要求

- R2-T3 原「pending → 胜出且不抛错」改为「pending → 等待 → 超时仍 pending 才胜出」；
- 新增：pending 期间收到更小 `tabId` → 判定 `lost`，不入队；
- 新增：等待期间 `connection/reset` 或卸载 → 取消等待、不写状态；
- 新增：等待产生的延迟 ≤ `claimWindowMs`；
- 原 129 条不得回退。

## 7. 影响

| 面 | 变更 |
|---|---|
| 契约 | ADR-011 的 pending 规则被本条取代 |
| 代码 | store 的 decide 尾段：pending 时延迟再判定 |
| 验收 | V21 复测：两标签只一个浮层、通知 ≤1 |
| 风险 | 延迟期间用户关闭标签/断连需正确清理（由 generation 守卫覆盖） |
