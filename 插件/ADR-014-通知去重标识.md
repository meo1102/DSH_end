# ADR-014：系统通知改用「每条唯一 tag」

| 项目 | 值 |
|---|---|
| 日期 | 2026-10-27 10:55（Asia/Shanghai） |
| 状态 | 已决定；待 V13 遮挡复测确认 |
| 取代 | v1.1 §6.6 第 4 步的 `tag='dsh-task-'+sessionId`；R1b-D1 的两版修复不再是根因解法 |
| 关联 | R1b-D1、V13、F9 |

## 1. 背景

V13「窗口被遮挡时无系统通知」两次修复（入队即通知、前台标志 + 微任务）均未解决。2026-10-27 带诊断日志的真机结果推翻了「遮挡/冻结」假设。

## 2. 证据

遮挡期间日志完整且时间连续：

```text
status:false      at=…179408   hidden:true hasFocus:false foreground:false
settle:schedule   at=…179409   (+1 ms)
decide            at=…179431   (+23 ms)
onEnqueued        at=…179432
notify:deliver    at=…179432
notify:delivered  at=…179434   permission:granted
```

用户手工四组对照（同一会话）：

| # | 构造 | 横幅 |
|---|---|---|
| 1 | `new Notification('T1',{body})`，无 tag | **有** |
| 2 | 固定 `tag='dsh-task-<sessionId>'` | 无 |
| 3 | 同 tag + `renotify:true` | 无 |
| 4 | 唯一 tag（`dsh-task-test-<时间戳>`） | **有** |

结论：Windows 把「用过的 tag」当作对已有通知的更新；`renotify` 不能恢复横幅。原设计「同会话共用一个 tag、只留最新一条」使该会话的第二次及以后完成永远静默。

这也解释了早先「可见未聚焦时通知正常」——那是该会话的**第一条**通知；之后都是更新。

## 3. 决定

通知 `tag` 改为**每条唯一**，并压到安全长度：

```text
tag = `dsh-task-${hash16(item.key)}`      // 9 + 16 = 25 字符
```

`hash16` 用两个不同种子的 FNV-1a 32 位拼成 16 位十六进制（纯函数、确定性、零依赖）。
`renotify` 保持 `false`（每条都是新通知，不需要 renotify）。

**长度约束（硬性）**：Electron 已知问题——Windows 11 上 `tag` 超过 **34 字符**即失效（[electron/electron#40433](https://github.com/electron/electron/issues/40433)）；WinRT `ToastNotification.Tag` 另有 64 字符上限（[文档](https://learn.microsoft.com/uwp/api/windows.ui.notifications.toastnotification.tag)）。因此：

- 禁止用 `sessionId + key` 直接拼接（本会话下约 105 字符，必失败）；
- 测试必须断言 `tag.length <= 34`，并在注释中标明来源。

## 4. 理由

- 唯一 tag 在 Windows 上稳定产生新通知，不依赖「更新已有条目」的未文档化行为；
- 与 F9「必达」一致；
- 应用层已有多重去重（3 s 冷却、`maxPerMinute`、`handled` 按 key），不依赖 OS 层 tag 去重。

## 5. 代价与边界

- 同一会话连续完成时，通知中心会出现多条（原先只有一条）。
- 原先「OS 层只留最新」的隐含承诺作废；这是有意取舍。
- 若将来要「只留最新」，必须另找机制（例如关闭旧通知 + 延迟新建），不再复用固定 tag。

## 6. 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 保留固定 tag + `renotify:true` | 实测无横幅 |
| 完全去掉 tag | 可行，但丢失会话前缀与分组信息，排查困难；唯一 tag 已足够 |
| 发送前 `close()` 旧通知再新建 | 仍复用同一 tag，Windows 仍可能视为更新；未验证且更绕 |

## 7. 影响

| 面 | 变更 |
|---|---|
| 契约 | v1.1 §6.6 第 4 步的 `tag` 写法更新；§7 未定义 tag，无需改 |
| 代码 | `client.js` 通知构造处一行；新增一条断言「同会话两条 item 的 tag 不同」 |
| 测试 | 原 128 + 1；`renotify:false` 仍断言 |
| 文档 | R1b-D1 缺陷文档需更正根因；交接文档待 V13 复测后更新 |
| 历史 | R1b-D1 两版修复（入队即通知、前台标志）本身不错误，保留；但它们不是根因解法 |

## 8. 未决

1. V13 遮挡复测是否恢复横幅（本次决定成立的前提）。
2. 通知中心条目增多是否可接受，需需求方确认。
3. `notify:delivered` 只表示「构造未抛错」，易误读；日志移除阶段一并改名为 `notify:constructed`。
4. `tag` 的 34 字符上限来自 Electron issue 与 WinRT 文档，本机尚未逐长度做边界实测；压到 25 字符后属安全区。
5. 32 位哈希的碰撞概率：同会话完成数在万级以下可忽略；若将来要求严格唯一，改用 64 位哈希（仍 ≤34 字符）。
