## 2. 根因

**Windows 对「已经用过的 tag」执行静默更新**（不重新提醒、不产生新横幅），`renotify: true` 也不改变这一行为（实验 3）。

原实现（修改前 `client.js:1768`）用 `tag: 'dsh-task-' + sessionId`，即「同一会话共用一条 tag、只留最新一条」。于是：

- 第一次完成：tag 首次出现 → 正常横幅；
- 同一会话第二次及以后完成：tag 已存在 → 静默更新 → 用户看不到任何提示。

这与缺陷现象「通知中心无记录 / 无横幅」、且「可见未聚焦首次正常」完全一致。前两版 R1b-D1 修复（`createForegroundTracker` 前台标志、后台 `queueMicrotask` decide、入队即通知）本身没有错，只是没有击中根因，**按裁决保留不删**。

## 3. 改动

### 3.1 `client.js`（两版，最终为 hash16）

**v1（已废弃，未真机）：** `tag: 'dsh-task-' + sessionId + '-' + key`。长度 ≈ 9 + 46（sessionId）+ 1 + 50（key）≈ **105 字符**，超过 Electron #40433 的 34 字符上限，必然失败（见 §9）。此版只保留为过程记录，代码已不再使用。

**v2（最终实现）：**

```diff
-            tag: `dsh-task-${item.sessionId ?? ''}`,
+            // V13 根因：Windows 对已用过的 tag 走静默更新，`renotify` 也不救。
+            // tag 压到 25 字符（9 前缀 + 16 哈希）以满足 Electron #40433 的 34 字符上限；
+            // 用 item.key 哈希保证同会话每条完成都唯一，避免第二次完成无声。
+            tag: `dsh-task-${hash16(item.key ?? '')}`,
             renotify: false,
```

- `client.js:93`–`112`：新增纯函数 `hash16(value)`（两个不同种子的 FNV-1a 32 位，拼成 16 位十六进制），并挂到 `__test__`（`client.js:2138`）供测试取用。
- `client.js:1789`–`1793`：最终 tag 公式；固定 `9 + 16 = 25` 字符。
- `item.key` 形如 `<sessionId>:<seq>`（`client.js:726`），由 store 的 `keySeq` 保证唯一；`enrich`/`defer`/`requeue` 均原样保留 `key`，因此延迟补发路径的 tag 也唯一且稳定。
- `renotify` 保持 `false`：每条都是新 tag，不需要 renotify。
- **未改**：`handled` 去重、`issued` 集合、claim/多标签、诊断日志、错误边界、`openSession`/点击回跳。

## 5. 行为变化（需要有意识接受）

- **通知中心不再「同会话只留最新一条」**：每条完成都是独立 tag，会累积多条记录。这是修复「第二次静默」的必然代价；若后续要求「只留一条，但每次都要有新横幅」，Windows tag 语义无法同时满足，需要重新设计（例如时间片 tag + 定期清理，但清理又会丢失历史，不建议）。
- `issued` 仍是按通知实例管理，`onclose`/点击时移除；tag 变化不影响该逻辑。
- tag 形如 `dsh-task-<16 位十六进制>`，固定 25 字符，**不含 sessionId**；排障时可用纯函数 `hash16(item.key)` 复算，不能从 tag 反查会话。
- V21 双标签「只一条通知」由 claim 决定，不受 tag 唯一化影响，但仍需复测。

## 9. 追加：tag 长度上限与 hash 方案（11:05）

### 9.1 长度上限来源

| 约束 | 上限 | 说明 |
|---|---|---|
| Electron web 通知（Windows 11） | **34 字符** | electron/electron#40433：`tag` 超过 34 字符即失效（不是截断，是不显示） |
| WinRT `ToastNotification.Tag` | 64 字符 | 更底层的限制，比 Electron 的 34 宽松；34 才是实际卡点 |

v1 的 `dsh-task-<46 字符 sessionId>-<~50 字符 key>` ≈ **105 字符**，无论按 34 还是 64 都超限，属于必然失败区间；这也是「打补丁后先别让需求方复测」的原因。

### 9.2 为什么不能用 sessionId 拼 key

- sessionId 在本机是 36–46 字符级（UUID/类似形态），key 是 `<sessionId>:<seq>`，本身又接近 50 字符。
- 两者拼接再加前缀至少 ~95–105 字符，**34 字符预算根本放不下**。
- 若截断 sessionId（如取前 8 字符）再拼 key，仍然超；只截 sessionId 会让跨会话 tag 冲突，只截 key 会让同会话不同条目冲突——唯一性无法保证。
- tag 带 sessionId 只对「肉眼排查」有帮助，不是功能必需；排障改用 `hash16(item.key)` 复算即可。

### 9.3 为什么选 hash16

- **长度确定**：`dsh-task-`（9）+ 16 = **25**，留 9 字符余量，不受 sessionId/key 长度影响。
- **确定性**：同一 `item.key` 恒得同一 tag；`enrich`/`defer`/`requeue` 都保留 `key`，所以延迟补发与首次发送的 tag 一致，不会一条通知两个 tag。
- **零依赖、纯函数**：两个不同种子的 FNV-1a 32 位（`0x811c9dc5`、`0x9e3779b9`）拼成 16 位十六进制；只用 `Math.imul`，无 `crypto`/第三方；可挂 `__test__` 直接测。
- **唯一性**：64 位空间；同一会话条目数是个位数到几十，碰撞概率可忽略。
- **可测**：正则 `^dsh-task-[0-9a-f]{16}$` + 长度 ≤34，单测可硬卡。

### 9.4 新 tag 示例

| key | hash16 | tag | 长度 |
|---|---|---|---|
| `k-1` | `a0a0699ce0761cf0` | `dsh-task-a0a0699ce0761cf0` | 25 |
| `s-1:0` | `e7d3363efd7614b2` | `dsh-task-e7d3363efd7614b2` | 25 |
| `s-1:1`（同会话下一条） | 另一值 | `dsh-task-<另一 16 位>` | 25 |

### 9.5 备选方案对比

| 方案 | 长度 | 唯一性 | 稳定性 | 结论 |
|---|---|---|---|---|
| `dsh-task-` + `at.toString(36) + '-' + seq` | ~21 | 同毫秒需靠 seq | 依赖 `at` 存在且不被改写 | 可行但不如 hash 稳，未采用 |
| `dsh-task-` + hash16(key) | **25** | 64 位 | `key` 在 defer/requeue 全程稳定 | **采用** |
| `dsh-task-` + 截断 sessionId + 截断 key | ~25 | 冲突不可控 | 需要额外冲突处理 | 否决 |

### 9.6 剩余风险

- 34 字符来自 Electron issue，本机 Electron 版本是否已修复未验证；25 字符在修复前后都安全。
- hash 不可读，排障需复算；已在 §5 记录。
- 通知中心仍会累积多条（§5）。
- V13 真机复测仍是唯一能证明「Windows 接受该 tag 并出新横幅」的环节。
