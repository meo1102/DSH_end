## 2. 代码现状地图（只列与本缺陷相关）

### 2.1 前台标志是怎么取的

| 位置 | 内容 | 关键点 |
|---|---|---|
| `client.js:1615`–`1655` `createForegroundTracker` | 单一布尔 `focused` | 初值取 `doc.hasFocus()`（1618–1622）；`window` 的 `focus` 置 `true`（1625–1627）、`blur` 置 `false`（1628–1630）；监听挂在 `window`（1634–1635）；`isForeground()` 返回该布尔（1643） |
| `client.js:1921`–`1927` `isForegroundPage` | `focused && !hidden && visibilityState === 'visible'` | 只有这一个函数同时看「事件标志 + 可见性」 |
| `client.js:1170` `createClientEnv.isForeground` | 注入 `isForegroundPage` | 供 store 的 `status:false` 快路径使用 |
| `client.js:1983` notifier `isForeground` | **注入的是裸 `foreground.isForeground()`**，不是 `isForegroundPage` | 两套前台定义不统一：notifier 自己在 1715–1716 另查 visibility/hidden，顺序为「先可见性、再事件标志」 |

> 与 v1.1 §6.6 第 1 步（`visibilityState !== 'visible' || hidden || !hasFocus()`）相比，当前实现用「blur 维护的标志」替代了「`!hasFocus()`」，这是第二版修复的刻意改动，也让 A 的成立条件完全集中在 blur 上。

结论：**遮挡是否会触发 `blur` 是整个第二版修复的唯一支点**。blur 不触发、visibility 也不变 hidden 时，插件内部没有任何状态能表示「被遮挡」。

### 2.2 settle → decide → notify 的实际链路

| 步骤 | 位置 | 说明 |
|---|---|---|

| `decide` | `client.js:670`–`745` | 685–690 记日志；711–713 是 `suppressWhenFocused`（默认 `false`，**不是本缺陷原因**）；725–735 入队；736–743 `onEnqueued` |

### 3.4 每支该看哪几个字段

| 分支 | 必看事件 | 判据 |
|---|---|---|
| **A** | `status:false` 的 `at`、`settle:schedule`、`decide`、`onEnqueued`、`notify:skip` | `status:false` 出现在完成时刻 **≤2 s**；`settle:schedule` 为 `foreground:true / mode:'coalesce-timer'`；`notify:skip reason:'visible-focused'`；三处 `visibilityState:'visible'`、`hidden:false`、`hasFocus:true` |
| **B** | `status:false` 的 `at` 与墙钟差、`settle:schedule` 的出现时刻 | `status:false` 只在**回到前台后**出现（与完成时刻差接近整个遮挡时长，且紧挨着 `focus`/visibility 恢复）；遮挡期间没有任何 `status:false`/`settle:schedule`/`decide` |
| **C** | `notify:deliver` + `notify:delivered` + `permission` | 有 `notify:deliver` 与 `notify:delivered`、`permission:'granted'`、**没有** `notify:skip visible-focused`；此时看系统通知中心 |

补充判读：

- `notify:skip reason:'visible-focused'` 只可能在 `isPageVisible()===true` 时出现；而 `isPageVisible` 要求第 1718 行 `isForeground()===true`，所以 **一旦出现该 skip，`foreground` 必为 true**——这本身就把 A 的「前台标志为 true」坐实，剩下的问题是它为什么在遮挡时仍为 true。
- 若 `settle:schedule` 是 `foreground:false / mode:'microtask'` 却仍无 `notify:deliver`：说明 `decide` 没跑到（`resolution`/认领/`minRunMs`/`sawRunning` 抑制），不是可见性问题，交 R5 另立缺陷。
- 若完全没有 `status:false`，先查 `status:true`（`running:true` 无日志，不好查）与会话是否真的结束；不属于 A/B/C。

## 4. A 分支：前台标志误判

### 4.1 现象签名

遮挡期间 `status:false` 已到、`decide` 已跑或只在 timer 到期后跑；三处快照都是 `visible / hidden:false / hasFocus:true / foreground:true`；`settle:schedule` 走 `coalesce-timer`；最终 `notify:skip visible-focused`；回前台卡片出现。

### 4.2 代码落点

| 落点 | 位置 | 现状 |
|---|---|---|
| 前台标志采集 | `client.js:1615`–`1655` | 只有 `window focus/blur`，无 `visibilitychange` |
| 前台判定的使用 1（settle 路径） | `client.js:803`、`816`–`820` | `isForegroundPage` |
| 前台判定的使用 2（通知 skip） | `client.js:1718`、`1825`–`1828` | 裸 tracker；**1825 就是 skip 行** |
| 事件监听缺口 | 全文件 | tracker 没有 `visibilitychange`/`pagehide`/`pageshow`；`focus` 只来自 `window` |

### 4.3 最小修法（分三层，按顺序决定）

**A-1（零风险，先做，无论最终成立与否）**

- tracker 增加 `document.visibilitychange`、`pagehide`、`pageshow`：可见性变化时同步刷新标志；`isForeground()` 改为「`focused` 且在可见时更新」；初始化仍用 `hasFocus()`。
- **记录「最近一次 blur / focus 时间」**（`lastBlurAt`、`lastFocusAt`），判定时用「`lastBlurAt > lastFocusAt` ⇒ 后台」而不是只看布尔；这修的是「focus/blur 事件乱序或丢失导致的布尔粘滞」，**不是**「从未 blur」。
- notifier 的 `isForeground` 改为注入 `isForegroundPage`（`client.js:1983`），去掉两套定义；这样 A-2 的新信号能同时作用于 settle 路径与 skip 判定。
- 收益：修掉「hidden 但 tracker 仍 true」的漏判，以及「focus 事件缺失导致 deferred 永不重试」（`onVisible` 在 1842 行被 `isPageVisible` 卡住）。
- **重要**：如果真机是 A2（`visible + hasFocus:true + 无 blur`），把 blur、`visibilitychange`、`document.hidden` 三者组合起来仍然全是「前台」，A-1 不会让 V13 通过；它只是 A-2 的前提与低风险兜底，不能拿它当 A 的完整修复。

**A-2（真正的遮挡代理；需架构评审，二选一）**

> 前提：真机日志证明 `hasFocus:true`、`hidden:false`、`visibilityState:'visible'` 且 **无 blur**。此时可见性 API 帮不上忙，只能在渲染进程里找「页面没在绘制」的代理信号。

- **候选 a（推荐）：`document.timeline.currentTime` 停滞检测**。完成时刻读一次 `document.timeline.currentTime` 与 `performance.now()` 比较，滞后 >1000 ms 视为「页面未绘制 → 后台」。
  - 优点：不轮询、不每帧计算、不加常驻监听，符合 C34；实现只有几行，且只在 `notify`/`settle` 判定时读一次。
  - 待验证：Electron/Chromium 遮挡时 `document.timeline.currentTime` 是否停在最后一帧（[待验证]，需真机先做一次 30 行临时探针，验证完删）；旧引擎可能返回 `null`。
- **候选 b：1 s 心跳 + 缺口检测**。自调度 `setTimeout` 写 `lastTickAt`，完成时若 `now - lastTickAt > 2000 ms` 视为后台。
  - 缺点：属于「轮询」范畴，可能触发 C34 评审意见与 C33 的常驻计时器计数；只在 v1 的 250 ms timer 被节流这条证据上成立；误判窗口大于 a。
- **候选 c：用户在场事件窗口**（`focus`/`pointerdown`/`keydown` 记 `lastActiveAt`）。误判率最高（用户长时间盯着输出不输入任何事件），**不建议**；仅作为 a/b 都不通时的最后手段。

**A-3（策略兜底，需 ADR）**

- 把 `auto` 改成「无法确认在前台就发通知」。这会直接违背 V13 的另一半「可见且聚焦 → 仅浮层」，属于契约变更，必须 ADR + 需求方签核；只在 a/b 都不可行时提出。

### 4.4 会引入的误判风险

| 风险 | 触发条件 | 方向 | 缓解 |
|---|---|---|---|
| 长任务阻塞主线程 >1 s（a）/ >2 s（b） | 大量同步渲染、GC | 假阳性：用户在看也发通知 | 阈值放宽到 2 s；一次任务最多一条；tag 去重 |
| 虚拟桌面切换/显示器休眠/锁屏 | 页面不绘制 | 假阳性 | 可接受：用户本来不在看 |
| 部分遮挡、窗口在另一屏但可见 | 不绘制？ | 视实现，可能假阳性 | 记录为限制；`systemNotification:'never'` 可整体关闭系统通知 |
| 遮挡但 Chromium 仍持续合成 | 遮挡检测未启用 | **假阴性：仍然漏** | a 的预验证就是为排除这条；若仍继续绘制，A-2 失效，转 A-3 或 B |
| `suppressWhenFocused:true` 用户 | 新信号绕过 focus | 语义冲突 | 明确抑制优先：`suppressWhenFocused` 仍按 `isFocused` 短路（711–713），不看新信号 |
| 回前台后重复通知 | `handled` 已被 prune | 重复 | 现有 `handled` 只在条目离开队列时删除（2060–2065），遮挡期间条目在队列中，安全；加 V13 复测断言 |

### 4.5 测试影响（先不改，等结论）

- `presentation.test.js:777`（D1-4）已覆盖「hasFocus=true 但 blur」；A-2 需新增「visible+focused 但 timeline 停滞 / 心跳缺口」用例，并断言 `notify:delivered` 只调用一次。
- `store.test.js:548`（D1-7）不受影响。
- A-1 会改变 `createNotifier` 的 `isForeground` 注入来源，`test/notifier.test.js` 与 `harness.js` 需同步（不改断言语义，只改注入形态）。

### 4.6 验收判据

遮挡 10 s 内：通知中心 1 条；`notify:delivered` 存在；回前台卡片在；同一任务不出现第二条；可见聚焦时仍只有浮层（无通知）。

## 5. B 分支：事件队列冻结

### 5.1 现象签名

- 完成时刻 ~ 遮挡期间：**没有任何** `status:false`/`settle:schedule`/`decide`/`onEnqueued`/`notify:*`。
- 切回前台后，`status:false` 与 `settle:schedule` 成簇出现（`at` 与墙钟差可达数十秒），随后 `decide` → `onEnqueued` → `notify:skip visible-focused`（因为此刻页面确实可见且聚焦）。
- 区分「只延迟了 `status:false`」与「整个运行都在遮挡中开始」：后者 `status:false` 的 `mode` 是 `unknown`，且 `minRunMs`（默认 1500 ms，判定在 709 行）会让 `decide` 直接 `finish`，**连卡片都不会出现**。缺陷现象里卡片在 → 只可能是 running:true 在遮挡前已收到。

### 5.2 客户端为什么无解

| 环节 | 位置 | 为什么救不了 |
|---|---|---|
| 事件源 | `client.js:1157` `ctx.remote.$on` | 事件不派发，`onStatus` 根本不执行 |
| 计时器/microtask | `client.js:752`–`768`、`806`–`814` | 没有任务在跑，微任务也不会被调度；timer 冻结时同样不执行 |
| 通知构造 | `client.js:1766` | `Notification` 只能由渲染进程 JS 调用；渲染冻结时无人调用 |
| 客户端自检 | 1713–1721 | 只能看 visibility/focus，不能证明「进程是否在跑」；等它恢复时页面已可见 → skip |

结论：**只要「渲染进程整体冻结」，任何客户端补丁都无解**。这也是缺陷文档里「若 `status:false` 只在回前台出现，需宿主侧方案」的严格含义。

### 5.3 若走宿主侧方案需要什么

宿主已经有独立的完成信号（不依赖渲染进程）：

| 已有能力 | 位置 | 说明 |
|---|---|---|
| `ctx.on('session/event', ...)` | `index.js:56`–`60` | 宿主已能识别 `turn/end` 并写 ring table（`toOutcomeEntry`） |
| 结果表 | `lib/outcome-table.js` | 已有 TTL/容量；可扩展为「完成事件队列 + 序号」 |
| 结果路由 | `index.js:67`–`80`、`lib/host.js` | 现有的是**拉取**（客户端 `fetch`），不是推送 |

要变成「遮挡期间也能提示」，需要三件事：

1. **宿主新通道**（三选一，均需 ADR-014）：
   | 方案 | 机制 | 代价/风险 | 证据 |
   |---|---|---|---|
   | Remote 事件（S1） | 宿主注册 Remote 事件，客户端 `ctx.remote.$on` 订阅 | ADR-001 已明确否决同类通道用于结果；需验证插件宿主能否自定义事件名并被客户端收到 | `typertGateway.registerRemoteEvents` 存在（本机 inspection，`[待验证]` 插件的注册资格与事件命名契约） |
   | SSE 路由（S3） | `webServer.register` 的 `prefix` 路由写 `text/event-stream` | `EventSource` 不能带请求头，鉴权只能靠 Cookie；断线重连/补发/多标签扇出都要自建（ADR-001 的三项成本） | ADR-001、v1.1 §4.3 |
   | WS 升级 | `webServer.registerUpgrade`（`WebUpgradeRoute`） | 鉴权与生命周期更重，等于自建连接层 | 宿主 inspection 有该方法，`[待验证]` 与 DSH 连接层的兼容性 |
2. **客户端降级**：新事件到达时，若本地 store 尚未收到 `status:false`，先按 `sessionId + 序号` 生成临时 item 并直接通知；`status:false` 到达后用同一去重键合并，不重复弹、不重复通知。
   - 需要扩 `Item` 契约（`§7.5`）与 `handled` 去重键：现在 `key = sessionId:seq`（725–726 行），宿主事件没有这个 `seq`；多标签认领（ADR-011）也要决定「宿主事件由哪个标签消费」。
3. **可观测性**：宿主侧完成事件的时间戳要能进日志（新增日志/诊断字段，需 C32 合规，不含标题）。

### 5.4 关键限制：宿主推送也解决不了「全冻结」

- 宿主推送仍要渲染进程执行 `new Notification`；若渲染进程冻结，推送只是**排在同一个队列里**，回前台才处理 → 仍然 skip。
- 真正能在冻结期间弹 Windows 通知的只有 **Electron 主进程 / 原生通知**，这需要改 DSH 源码或引入原生依赖，两者都在本项目禁区（不改 DSH、零第三方依赖）。
- 因此 B 的宿主方案只在「**事件通道被节流、渲染进程仍在跑 JS**」时有效；如果日志证明连 `decide` 都能在遮挡期跑（只是事件晚到），宿主推送也只会把「晚到」提前，不能保证「遮挡期发出」。

### 5.5 粗略工作量与风险（供架构决定是否开 ADR-014）

| 项 | 估算 |
|---|---|
| ADR-014（通道选型、Item/去重/多标签契约、失败路径） | 0.5–1 人日（含评审） |
| 宿主：完成事件队列 + 通道注册/清理 + 单测 | 1–1.5 人日 |
| 客户端：订阅/降级/去重/多标签 + 单测 | 0.5–1 人日 |

**建议**：除非日志明确显示「`status:false` 只在回前台出现、且遮挡期间连 microtask 都没跑」，否则**不要开 ADR-014**；优先按 §7 的「环境/平台限制」挂账，或向 DSH 提「主进程通知」需求。

## 6. C 分支：通知已发但被系统吞

### 6.1 日志签名

| 事件 | 期望 |
|---|---|
| `settle:schedule` | 任意（通常 `foreground:false / mode:'microtask'`） |
| `decide` → `onEnqueued` | 有 |
| `notify:deliver` | **有**（`systemNotification:'auto'`） |
| `notify:delivered` | **有**，`permission:'granted'` |
| `notify:skip` | **无**（尤其没有 `visible-focused`） |

满足以上仍无通知中心记录，才是 C。

### 6.2 怎么确认（按顺序，5 分钟）

1. 检查 Windows「通知中心」是否有**同 tag 的旧记录**：`tag = 'dsh-task-<sessionId>'`（`1768`）+ `renotify:false`（`1769`），同一会话重复完成时 Windows 可能「更新旧条目而不重新提醒」——看起来像没有新通知。清空通知中心后重测一次即可排除。
2. 检查专注助手/勿扰（含「仅闹钟」「全屏时」规则）与「通知和操作」里 DSH/Electron 的开关；记录测试时刻的系统状态。
3. 遮挡状态下直接在控制台 `new Notification('遮挡测试')`：能弹 → 排除系统层；不能弹 → 环境限制（v1.1 §10.7 已规定「专注助手/企业策略吞通知 → 记录为环境限制，不计缺陷」）。
4. 看通知归属应用：若落在「Electron」或未注册 AUMID，`V13` 的「通知中心 1 条」口径可能要按环境修正（§10.7 同款）。

### 6.3 可改的验收口径（三选一，建议 1+3）

1. **拆分「已发出」与「已显示」**：插件侧判据 = `notify:deliver` + `notify:delivered` + `permission:'granted'` + 无 skip；系统侧判据 = 通知中心 1 条。V13 的 P1 只卡前者，后者记录为环境观察。
2. **按 §10.7 记环境限制**：若专注助手/策略开启导致吞通知，V13 记「有条件通过（环境限制）」，不计缺陷；恢复系统设置后补测。
3. **改测试/验收步骤**：先清空通知中心再测；把「同一 tag 的更新」计入「1 条」；在 `V13` 记录里固定写 Windows 版本、专注助手状态、`permission`、`notify:delivered` 日志。

### 6.4 代码层候选（不现在做）

- 把 `renotify` 改为 `true`（同一 tag 也重新提醒）→ 会改变 `§6.6` 第 4 步契约，需 ADR；且可能造成骚扰。
- 记录 `notification.onshow`/`onerror`（Electron 支持）到临时日志 → 区分「构造成功但未显示」；属于诊断增强，随 §9 一并清理。

## 8. 我的判断：A 最可能

**依据（代码假设）**：第二版修复把「遮挡」完全等价于 `window.blur`，这是 `client.js:1628`–`1635` 唯一的状态写入点，也是 `803`（是否走 microtask）与 `1718`（是否 skip）的唯一输入。代码里**没有任何**路径能表示「`visible + hasFocus + 被遮挡`」——一旦 Electron 不上报 blur（Windows 遮挡时 `hasFocus()` 仍为 true 是缺陷文档已记录的现象），`foreground` 恒为 true，`settle:schedule` 走 `coalesce-timer`，通知在 1825 行被 skip，现象与 v1 完全一致。v2 尚未真机验证，所以「修复无效」的最简解释就是它依赖的那条假设不成立。

**为什么不是 B**：B 要求渲染进程的事件派发被冻结。但 Electron 的后台节流主要作用于 timer/rAF，`ctx.remote` 的 IPC/WS 消息通常仍会派发；而「回前台卡片存在」说明 running:true 早已收到、状态机在跑。B 需要的强假设（整个事件队列冻结）比 A 需要的假设（遮挡不触发 blur）更少见。若日志显示 `status:false` 只在回前台出现，则立刻改判 B，并停止客户端侧改动。

**为什么不是 C**：可见未聚焦时通知能正常出现，说明构造与系统投递链路可用；`notify:delivered` 尚未在任何一次遮挡测试中被观察到（v1 没有该日志，v2 未测）。C 只有在「日志证明已发出」后才成立。

**置信度**：中等。A ≈ 50–55%，B ≈ 30–35%，C ≈ 10–15%。**结论完全可被 §7 的日志推翻**，这正是本文先写日志判读的原因。
