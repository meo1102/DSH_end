## 1. 根因

`resolve` 在 `status:false`（观察窗起点）**立即**执行；此时本轮 `turn/end(aborted)` 可能尚未写入会话事件流：

- 快路径「取最后一条 `turn/end`」读到**上一轮**的 `completed`；
- 慢路径宿主结果表按会话覆盖写，`GET` 返回的也是上一轮条目；
- `resolutionPromise` 一旦完成即锁定，250 ms 后 `decide` 直接采用陈旧结果。

所以问题不是抑制逻辑，而是**结果没有新鲜度约束**。

## 2. 实现

### 2.1 store：传入 `since`

`client.js:607`：

```js
promise = env.resolve(id, controller === null ? undefined : controller.signal, state.startedAt);
```

`state.startedAt` 在 `status(true)` 时记录；§8.3 抑制顺序、状态机与 decide 规则均未改。

### 2.2 resolver：新鲜度 + 重试

| 位置 | 内容 |
|---|---|
| `client.js:1050`–`1051` | `SKEW_MS = 100`、`RETRY_MS = 40` |
| `client.js:1060` | `isFresh(stamp, since)`：`since` 非数字时不过滤（旧调用/测试兼容）；否则要求 `stamp >= since - SKEW` |
| `client.js:1066` | `eventTime(entry)`：取 `entry.event.time`，兼容外层 `entry.time` |
| `client.js:1073` | 快路径从后往前找**新鲜**的 `turn/end`；陈旧项跳过，无命中返回 `undefined` |
| `client.js:1097` | 慢路径单次尝试：`since` 为数字时只接受 `body.at >= since - SKEW`；陈旧/缺失 `at` 返回 `stale` |
| `client.js:1142` | `resolve(sessionId, signal, since)`：循环重试；成功保留 `source='binding'/'route'`，只有最终降级是 `fallback` |

### 2.3 重试时序

```text
t=0    attempt 1（binding → route）
t=40   attempt 2
t=80   attempt 3
t=120  attempt 4
t=160  attempt 5
t=200  预算耗尽 → { outcome:'completed', source:'fallback' }
```

- 预算 `resolveBudgetMs`（默认 200 ms）由原有预算计时器控制；重试间隔 40 ms。
- 每轮最多 5 次重读（符合 ADR 的代价估计）；总时延仍在 P95 ≤ 500 ms 内（250 ms 观察窗内完成）。
- 外部 `signal` 取消或预算超时：共享 `AbortController` 立即 abort 在途 fetch，清掉重试计时器并返回；取消时不进入下一轮。
- `since` 缺省（旧调用）时不重试、不过滤，保持原有单次行为（R01–R10 全部保持）。

## 4. 未覆盖 / 风险

- **真实落盘延迟未测**：ADR 假设 `turn/end` 与本轮状态变化同为毫秒级；若真实落盘 >200 ms，仍会走 `completed/fallback`（ADR 明确保留该降级）。
- **事件时间字段位置**：实现按 ADR 取 `entry.event.time`，并兼容 `entry.time`；真实 `SessionEventWindow` 是否稳定提供该字段需 V12 真机确认（缺字段会被视为陈旧 → 重试 → 最终 completed）。
- **宿主路由 `at` 语义**：假定为 epoch ms 且每轮更新；V12 重测时若宿主条目 `at` 仍是旧值，重试会一直 stale，最终 fallback。
- V12 真机复测：发消息 → 立刻 Stop → 期望**不弹**；若仍弹，需带 `suppressed`/`completed` 与 route/binding 来源日志（当前无 debug 日志，需临时取证）。
- 未改 tag/hash16、claim、notifier、渲染结构、字典、`decide` 规则顺序。

## 6. V12 复测追加：探针与静态确认（2026-10-28 11:45）

### 6.1 发现并修复的接线缺陷

复测仍失败的直接原因之一：`createClientEnv` 的 resolver 包装只转发两个参数：

```js
// 修复前
resolve: (id, signal) => resolver.resolve(id, signal)
```

store 虽然传了第三个参数 `state.startedAt`，但在这里被丢弃，resolver 收到的 `since` 恒为 `undefined`，于是**新鲜度过滤与重试从未生效**（表现为仍采用上一轮 `completed`）。已改为：

```js
resolve: (id, signal, since) => resolver.resolve(id, signal, since)   // client.js:1325
```

探针里对照 `resolve:start.since` 与 `resolve:attempt.since` 即可验证是否还有同类丢参。

### 6.2 一次性探针

统一 `console.debug('[tct]', payload)`，每处 `try/catch`，不参与任何判定：

| 事件 | 位置 | 字段 |
|---|---|---|
| `resolve:start` | `client.js:616` | `since`、`now`、`sessionIdTail` |
| `resolve:attempt` | `client.js:1234` | `n`、`source:'binding'`、`fresh`、`sawCount`、`lastTime`、`since`、`now` |
| `resolve:route` | `client.js:1251` | `n`、`status`、`at`、`fresh` |
| `decide` | `client.js:798` | `outcome`、`source`、`elapsed` |

- `sawCount`：本次扫描到的 `turn/end` 条数；`lastTime`：最后一条的 `event.time`（无则 `null`）。
- `decide.source` 来自 resolver 返回值（`state.resolution.source`；pending 时为 `null`）。

### 6.3 静态确认结论

**① 客户端 `SessionEventWindow.entries` 的时间字段**

结论：命中 `entry.event.time`；`entry.time` 只是兼容分支，未使用。

依据（从本机 `app.asar` 读取的 DSH 源码）：

- `@deepseek-ai/dsh-api-session-controller/lib/client.js` 的 `MutableSessionEventSource` / `windowSnapshot`：`entries` 是窗口条目；历史与直播条目形状为 `{ type: 'event', event }`，瞬时条目为 `{ type: 'transient', event }`（`visible.push({ type:'transient', event:{…} })`）。我方代码只接受 `entry.type === 'event'`，因此天然跳过 transient。
- `@deepseek-ai/dsh-session/lib/types/index.js` 的事件信封校验把 `time` 作为**必填**字段：`case 'time'`，且 `typeof time !== 'number' || !Number.isSafeInteger(time)` 直接判非法。
- 因此实际命中 `entry.event.time`；`entry.time` 分支在真实数据上不会命中。

**② 宿主路由 `at` 是否每轮更新**

结论：**每轮新 `turn/end` 都会刷新 `at`**；`event.time` 缺失时用宿主 `now()` 也只会给**新条目**一个新时间，不会让旧条目变“新鲜”。

依据：

- `lib/host.js:61`：`const at = Number.isFinite(event.time) ? event.time : now();`。`session/event` 的 `event.time` 由事件信封保证（safe integer，epoch ms；WP1 真机已见 `1793002859374`）。
- `lib/outcome-table.js` 的 `put`：同 `sessionId` 先 `delete` 再 `set(entry)`，条目对象由本次 `toOutcomeEntry` 新建；旧条目的 `at` 不会被改写。
- 路由 `200` 必然带 `at`（`exposeReason` 开关只影响其他字段）；客户端按 `at >= since-100` 过滤。
- 边界：若把**旧事件对象**重新投递（重放）且 `event.time` 缺失，则 `at=宿主接收时刻` 会被判新鲜——这是唯一可能“旧结果变新”的路径，正常 turn 流不会发生。

### 6.5 复测判读

刷新 → 发消息 → 立刻 Stop，贴 `[tct]`：

| 现象 | 判读 |
|---|---|
| `resolve:start.since` 是数字，`resolve:attempt.since` 也是同一数字 | 接线正确 |
| `attempt.since` 为 `null` 或与 `start` 不一致 | 仍有丢参/替换，回到 6.1 |
| `lastTime` 为 `null` | 真实条目没有 `event.time`（与静态结论矛盾，需要看 `sawCount`/条目形状） |
| `lastTime` 远小于 `since`（例如差一个数量级） | 时钟/单位不一致（秒 vs 毫秒）或 `since` 取错 |
| `fresh:true` + `decide.outcome:'suppressed'` | 修复生效，V12 应不弹 |
| `resolve:route.at` 远小于 `since` | 宿主表仍是旧条目，需查宿主 `put` 时机 |
| `decide.outcome:'completed'` + `source:'fallback'` | 预算耗尽仍无新鲜结果（ADR 保留降级） |

## 7. V12 通过 + 探针移除（2026-10-28 11:50）

### 7.1 真机日志（决定性）

```text
resolve:start   since=1793158050674 now=1793158052271
resolve:attempt n=1 source=binding fresh=false sawCount=14 lastTime=1793085137678
resolve:route   n=1 status=200 at=1793158052268 fresh=true
decide          outcome='suppressed' source='route' elapsed=1860
```

判读：

| 数值 | 结论 |
|---|---|
| `since=1793158050674`，`now-since=1597 ms` | store 传入的 `since` 是**本轮 running 起点**，单位 epoch ms |
| `lastTime=1793085137678`，比 `since` 早 **72,912,996 ms ≈ 20.25 小时** | binding 快路径窗口里的最后一条 `turn/end` 是**很久以前**的；`sawCount=14` 说明扫到 14 条，但没有一条满足 `since-100` |
| `resolve:route at=1793158052268`，比 `since` 晚 **1594 ms**，`fresh=true` | 宿主路由返回的是**本轮** `turn/end`（aborted/user），被接受 |
| `decide outcome='suppressed' source='route' elapsed=1860` | 最终用路由结果抑制，V12 不弹 |

结论：**本环境的 binding 快路径窗口是陈旧的**（最后 `turn/end` 早约 20 小时，sawCount=14），正确性实际由宿主路由承担；快路径只作为“会话仍 retain 且事件新鲜”时的兜底。这与 ADR-016 不冲突——新鲜度过滤把不可信的 binding 结果挡掉，交给 route。

### 7.2 为什么“加了 ADR-016 仍失败”

两个独立原因叠加：

1. **第一层（原始缺陷）**：resolver 没有新鲜度，直接取最后一条 `turn/end`（上一轮 completed）/ 宿主表上一轮条目。
2. **第二层（接线缺陷，本次探针阶段发现）**：`createClientEnv` 的 wrap 只转发 `(id, signal)`，把 store 的第三个参数 `state.startedAt` 丢掉；resolver 的 `since` 恒为 `undefined`，于是 ADR-016 的过滤与重试**在端到端路径上从未生效**。
   - 现象上仍然是“采用陈旧 completed”，不是 fallback；此前“全部判陈旧走 200 ms 兜底”的判断只对 binding 一半成立——真正修好转发后，binding 确实陈旧，但 route 是新鲜的，因此直接 `suppressed`。
3. 修复转发（`resolve: (id, signal, since) => resolver.resolve(id, signal, since)`）后，探针第一轮即通过。
