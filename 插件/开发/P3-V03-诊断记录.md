## 1. 现象与待验证假设

- 会话名取到真名（`确认插件项目信息`），**工区名回落 `未分组`**；说明 `useSessions` 链路可用，`workspaces` 侧是空/形状不符。
- `resolveNames` 现假设：快照是数组、`{byId}`（对象或 Map）、或 `{workspaces}`；每条工作区有 `sessionIds`（数组/Set）或 `sessions`（数组），名称取 `title → name → path 末段`。
- 失败可能来自：① `useWorkspaces` prop 根本没到组件（当前 `apply` 的 `BoundToastHost` 没有显式传它）；② 快照是 `null`/空；③ 快照是别的形状（如顶层 Map、`{list}`、行字段叫 `sessionIds` 之外的名称）；④ 行里有 `sessionIds` 但不含当前会话。

探针只回答「形状」，不猜原因。

## 2. 日志位置与触发

- 代码：`client.js` 的 `ToastHost`，首个有 item 的渲染后 effect；每个 `item.key` 只打一次（`useRef` + `Set`）。
- 输出：`console.debug('[task-complete-toast]', { event: 'workspace:probe', … })`。
- 触发方式：刷新页面 → 正常触发一次任务完成 → 卡片出现时输出一行；同一 item 不再重复。刷新页面会重置去重。
- 失败隔离：整段 `try/catch`，探针异常不影响渲染、通知与 claim。

## 4. 如何判读

| 观察 | 结论 | 下一步 |
|---|---|---|
| `useWorkspaces: 'undefined'` | prop 没到 `ToastHost`（`apply` 的 `BoundToastHost` 未透传，或插槽未提供） | 修 `apply`/插槽接线，而不是改 `resolveNames` |
| `useWorkspaces: 'function'` + `workspaces.kind: 'null'` | hook 存在但快照为 null | 查该 hook 的就绪时机/是否需要 selector |
| `kind: 'array'` + `rowCount > 0` + `firstWorkspace.keys` 里没有 `sessionIds` | 行结构与假设不符 | 用 `keys` 里的真实字段名改 `workspaceHasSession` |
| `firstWorkspace.keys` 有 `sessionIds` 但 `containsSession: false` | 关联字段存在但没挂当前会话 | 看 `sessionIdsLength`/是否为数组；可能是别的会话或空数组 |
| `kind: 'object'` + `keys: ['byId', …]` | 是 byId 快照；若 `rowCount` 正确，问题在行字段 | 对照 `firstWorkspace.keys` |
| `kind: 'map'` | 快照本身就是 Map | `workspaceList` 目前只处理 `snapshot.byId` 的 Map，顶层 Map 会返回 `[]`——真凶候选 |
| `kind: 'object'` + `keys` 是工作区 id 列表 | 快照是「id → 行」的普通对象 | `workspaceList` 会 `Object.values`，可能可用；问题在行字段或名称字段 |
| `containsSession: true` 但工区仍回落 | 找到了行，但名称字段不在 `title/name/path` | 用 `firstWorkspace.keys` 找真实名称字段 |
| `sessions.keys` 与预期差异大 | `sessionRow` 的 `byId` 假设也需复核（本次先不动） | 另开诊断，不混入 V03 |

## 8. probe v2（14:30 追加，等待第二次真机触发）

### 8.1 v1 结果与探针自身的偏差

真机 v1（需求方）：

```json
"workspaces": { "kind": "object", "keys": ["items","archivedSessionIds","pinnedSessionIds","state","phase","error"], "keyCount": 6 }
"firstWorkspace": { "kind": "array" }
"containsSession": false
```

- 顶层字段说明真实快照是 **`{ items, archivedSessionIds, pinnedSessionIds, state, phase, error }`**，工作区行在 `items` 里。
- v1 的 `firstWorkspace` 取到的是 `items` **数组本身**：v1 的摊平逻辑只认 `byId`，其余对象走 `Object.values()`，第一个值正好是 `items`。所以 `kind: "array"`、`sessionIds` 不存在、`containsSession:false` 是探针偏差，不是事实。
- 已确认的事实：快照不是裸数组、不是 `{byId}`；`resolveNames` 的 `workspaceList` 只认数组/`byId`/`workspaces`，因此返回 `[]` → 工区名回落。

### 8.2 v2 改动（仍只改探针，不改解析）

| 位置 | 改动 |
|---|---|
| `probeWorkspaceRows` | 优先识别 `snapshot.items` 数组，再回退 `Map`/`Set`/`byId`/`workspaces`/普通对象；修正 v1 的「取到 items 数组」偏差 |
| `probeItems` | 新增 Q1：`items` 是否存在、是否数组、`length` |
| `probeRow` | 字段名上限从 8 提到 **12**；新增 `sessionLikeKeys`（名字里含 `session` 的字段名，最多 12 个） |
| `probeSessionRow` | 新增 Q4b：取 `sessions.byId[sessionId]`（兼容 Map/对象/数组），输出 `found`、前 12 个字段名、`workspaceLikeKeys`（名字含 `workspace`）、`hasWorkspaceId`（`in` 判断） |
| `createWorkspaceProbe` | 载荷改为按当前 item 生成，包含 `containsSession` 与会话侧反查 |

### 8.3 v2 日志字段

| 字段 | 说明 |

### 8.4 v2 判读

| 观察 | 结论 |
|---|---|
| `itemsProbe.isArray:true` + `firstItem.keys` 有 `sessionIds` + `containsSession:true` | 行结构正确，问题只在 `workspaceList` 不认 `.items`；修 `workspaceList` 即可 |
| `firstItem.keys` 没有 `sessionIds`，但 `sessionLikeKeys` 有别的名字（如 `sessions`） | 按真实字段名改 `workspaceHasSession` |
| `containsSession:false` 但仍可能正确 | 当前会话确实没挂到任何工区；或 `sessionIds` 值类型不是数组/Set（看 `sessionIdsIsArray/Length`） |
| `sessionRow.hasWorkspaceId:true` 或 `workspaceLikeKeys` 非空 | **优先改从会话侧反查**：`resolveNames` 先用 `sessions.byId[sessionId].workspaceId` 找工区，再取名称，不再全量扫工区 |
| `sessionRow.found:false` | 会话行不在 `byId`（可能是 Map/其他键），或 `useSessions` 形状不同；看 `sessions.kind/keys` |
| `firstItem.keys` 名称字段可能叫 `name`/`title`/`path`/`label` | 名称解析按真实字段扩展 `workspaceTitle` |
