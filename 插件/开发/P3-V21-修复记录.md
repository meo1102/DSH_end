## 1. 现象

两个标签同一次完成（一个前台、一个后台），**两个标签都入队**，前台出现两条浮层（第二条会话名回退「未分组」，因为后台标签缺工作区快照）。

需求方日志：

```text
status:false   at=…468
decide         at≈…489  (+21 ms)  → claim-pending-at-decide
onEnqueued     at=…489  hidden:true   // 后台标签也入队
```

## 2. 根因（时序算术）

| 量 | 值 |
|---|---|
| `status:false` 到达 | T |
| 后台路径 `decide`（`queueMicrotask`） | T + ~21 ms |
| 认领窗 `claimWindowMs` | 80 ms（ADR-011） |
| decide 时剩余窗口 | ≈ 80 − 21 = **59 ms > 0** |
| 旧规则 | `claim === 'pending'` → **按胜出处理** |

所以**每一次后台 `decide` 都必然看到 pending**，而 pending 被定义成胜出 → 两个标签都赢。这不是抖动，是实现与旧契约共同造成的结构性缺陷：认领窗比判定晚约 59 ms，从来来不及。

## 3. 实现（ADR-015）

### 3.1 新增状态

| 字段 | 写入点 | 用途 |
|---|---|---|
| `state.claimStartedAt` | `startClaim`（`client.js:649`，取 `now()`） | 计算剩余窗口 |
| `state.claimWaited` | `startClaim` 置 `false`（645）；`waitForClaim` 置 `true`（689） | 防止二次判定再次延迟成死循环 |
| `state.awaitingClaim` | `waitForClaim` 置 `true`（690）；二次判定/`decide` 入口清 `false` | 让「窗口内提前 resolve」能立刻二次判定 |

### 3.2 代码落点

| 位置 | 改动 |
|---|---|
| `client.js:642`–`666` `startClaim` | 记录 `claimStartedAt`；promise 的 `then/reject` 改为调用 `settleClaim`，不再直接写状态 |
| `client.js:670`–`680` `settleClaim`（新增） | 先按 `state/generation` 守卫写结果；若正在等待，取消等待计时器并**立即** `decide`（ADR-015 第 3 点：窗口内提前 resolve 不必等满 80 ms） |
| `client.js:687`–`698` `waitForClaim`（新增） | 恢复 `mode='settling'`，把延迟放进 `state.timer`，时长 `min(remaining, claimWindowMs)`（≤80 ms）；到期清标记后 `decide` |
| `client.js:752`–`760` `decide` 的 claim 分支 | `pending && !claimWaited` 且 `remaining > 0` → 等待并 `return`（不入队、不记诊断、不碰冷却/发射计数）；`remaining ≤ 0` 才落降级 |
| `client.js:761`–`768` | 诊断 `claim-pending-at-decide` 只保留在**真降级**（窗口结束仍 pending）路径 |
| `client.js:735`–`740` `finish` | 增加 `clearSettle(state)`，显式取消等待延迟后再清状态 |
| `client.js:728`–`730` `decide` 入口 | 清 `awaitingClaim`，避免残留标记影响下一次判定 |

### 3.3 取消与守卫

- **running 回弹**：`onStatus(running:true)` 走 `clearSettle`（取消等待计时器）→ `cancelClaim` → `abortResolution`；迟到 promise 由 `state.mode !== 'settling'` 丢弃。
- **connection/reset、卸载**：`store.reset()` 遍历 `states` 调 `clearSettle`/`cancelClaim`，再 `states.clear()`；迟到结果由 `states.get(id) !== state` 丢弃。
- **finish()**：先 `clearSettle`，保证不存在悬挂计时器。
- **二次判定**：只由 `claimWaited === true` 进入；不会再次 `waitForClaim`。

### 3.4 未改

`hash16`/tag、notifier、诊断日志格式、`handled`/`issued`、点击回跳、冷却/发射计数规则、claim 频道/消息/胜者规则（仍按 ADR-011）。

## 5. 未覆盖 / 风险

- **V21 真机复测未做**（需求方两个标签都开着、只发一次消息）。单元测试用同步伪 BroadcastChannel，真实 BC 是异步投递。
- **计时器同刻竞态**：等待计时器与租约的 80 ms 计时器同刻到期时，依赖「租约先注册、先触发 → promise 微任务 → `settleClaim` 立即判定」这一顺序。若极端调度下等待计时器先跑且 claim 仍 pending，会走真降级（双弹）。V21 重测时若仍双弹，先看两个标签是否都有 `claim-pending-at-decide`。
- **后台节流**：等待用 `setTimeout`；遮挡/后台标签的计时器节流可能让提示晚于 80 ms（预算仍 < 500 ms，但比旧路径慢）。V13 刚修复的「后台也提示」不受影响，只增加 ≤80 ms。
- **提前 resolve 的 won 分支**：代码与 T9（lost）共用 `settleClaim` 路径，未单独写 won 用例；T9 已覆盖「取消计时器并立即判定」。
- **卸载与 running 回弹的取消**：由 `clearSettle` 统一覆盖，未补专门用例；`reset` 用例（T10）覆盖同一取消路径。
- 未改 `claimWindowMs`、观察窗、通知/浮层语义。

## 6. 契约

- ADR-015 取代 ADR-011「decide 时 claim 仍在途 → 按胜出处理（降级）」；频道名、消息字段、胜者规则、`claimWindowMs` 不变。
- 单标签/无 `BroadcastChannel`：租约 `claim` 立即返回 `true`，不会进入等待，行为不变。
- V21 通过前，本文不构成真机验收结论。
