# G2-1 遮挡修复方案（已按人类指令实施，待复验）

> 证据：[`真机验收结果-2026-11-04.md`](真机验收结果-2026-11-04.md) §3 G2-1、§5-A；台账 D-002 / F-021。
> 结论：G2-1 是 R2（阻塞人类处理授权）；本轮按「进入会话即收起」修复，**尚未复验**，G2 仍不主张可用。

## 1. 人类裁决

- **不采用** `appearance.noticePosition` / 移动落点方案。
- **不要求常驻**；进入会话后卡片与系统通知收起即可。
- 保留：pending 解决/取消时移除、用户手动关闭、系统通知、跨标签通知去重、`notify.awaiting` 开关。
- 不读取授权/回答内容，不自动点击，不改宿主。

## 2. 已实施改动

### 2.1 信号

- `sessionIsEntered(snapshot, sessionId)`：只读 `sessions.list.byId[sessionId].retainedBy.mainView > 0`。
- `apply` 订阅 `ctx.sessions.list`（若可用）；列表变化时对每个提醒检查是否已进入会话。

### 2.2 行为

1. **已进入会话时出现 pending**：不显示提醒、不发系统通知（`onAdded` 直接 dismiss）。
2. **在别的会话时出现 pending**：显示提醒；用户进入目标会话（mainView>0）后，订阅回调调用 `notices.dismiss`，卡片收起。
3. `notices.dismiss` 触发 `onRemoved` → `notifier.close(item.key)`，同时关闭 Windows 通知中心里的对应通知。
4. 原 pending 解决/取消、手动关闭、`connection/reset` 行为不变。
5. 不做定时自动消失：避免后台/隐藏时计时器关闭系统通知，导致授权提醒被吞。生命周期由「进入会话/解决/手动关闭」结束。

### 2.3 不改的部分

- 不新增宿主 Config 字段；`appearance`/`notify` 不变。
- 不改 G1 完成提示、多标签认领、G3 外观。
- 不改 `真机验收结果-2026-11-04.md`。

## 3. 测试

- 新增 W15：启动时已在会话内，pending 到达不显示。
- P15：提醒卡内容/attention/名称不变。
- 全量：**160/160** 通过，`node --check 17/17`；无宿主配置变更，页面刷新即可加载新客户端代码。

## 4. 复验要求

1. 刷新页面。
2. 构造两种场景：
   - 已在目标会话内触发授权/回答 → 不应出现卡片/系统通知；
   - 在别的会话触发 → 出现提醒；进入目标会话 → 卡片和通知中心通知同时收起。
3. 重跑 G2-2~G2-6；G2-3 操作方式与截图补齐。
4. G3 仍等本修复复验通过后再重启宿主跑矩阵。
5. 若 `retainedBy.mainView` 不能代表“进入会话”，本修复无效；需回到独立落点方案，另行授权。

## 5. 剩余风险

- 依赖 `retainedBy.mainView` 这一客户端内部字段；DSH 升级需回归。
- 卡片可能出现短暂一帧再收起；未做动画级验证。
- 系统通知关闭依赖 `onRemoved` 路径；若通知尚未构造完成，close 为 no-op。
- 多标签：进入会话只影响当前标签；其他标签的提醒仍由各自列表状态决定（系统通知已认领）。
