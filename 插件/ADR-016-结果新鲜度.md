# ADR-016：结果必须新鲜——按 startedAt 过滤并重试

| 项目 | 值 |
|---|---|
| 日期 | 2026-10-28 11:20（Asia/Shanghai） |
| 状态 | 已决定，待实现 + V12 复测 |
| 关联 | V12、F1/F3、结果桥、ADR-004 |

## 1. 问题

V12（用户点 Stop）实测：停止后仍弹出「任务完成」卡片，第二行为正常名称。期望是**不弹**（`aborted/user → suppressed`）。

## 2. 根因

`resolve` 在 `status:false`（观察窗起点）立即发起；此时本轮的 `turn/end` 可能**尚未写入**会话事件流。快路径「取最后一条 `turn/end`」于是读到**上一轮**的 `completed`，分类为完成并锁定结果；250 ms 后 `decide` 直接使用该陈旧结果。

慢路径同理：宿主结果表按会话覆盖写，若宿主尚未收到本轮 `turn/end`，`GET` 返回的是上一轮条目。

即：**结果没有新鲜度约束**，任何「最近一次」的记录都会被当成本轮。

## 3. 决定

给结果加 `since` 约束（`since = 本轮 running 区间的 startedAt`）：

1. **快路径**：只接受 `event.time >= since - skew` 的 `turn/end`（`skew = 100 ms`）；没有满足条件的记录 → `unknown`。
2. **慢路径**：响应 `at >= since - skew` 才接受；否则 `unknown`。
3. **重试**：`unknown` 时在解析预算（`resolveBudgetMs`，默认 200 ms）内**每 40 ms 重试一次**，而不是立刻回退。
4. **预算耗尽仍 unknown** → 返回 `completed`（保留 v1 降级语义，宁可弹也不静默丢失）。
5. `since` 由 store 在 `status(true)` 时记录，随 `resolve` 传入；不改变 §8.3 的抑制顺序。

## 4. 理由

- 停止、失败这类结果本来就晚于「最近一次成功」，不做新鲜度判定必然误标为完成（F3 直接失效）；
- 200 ms 预算足够覆盖本机事件落盘延迟（V13 日志里 `turn/end` 与状态变化同为毫秒级）；
- 重试而非直接降级，把「未知」与「已确定为完成」区分开。

## 5. 代价

- 最坏情况下提示延迟增加至多 200 ms（仍在 P95 ≤ 500 ms 预算内）；
- 每轮最多 5 次重读（内存/本机请求，代价可忽略）；
- 需要新的测试夹具：可控「事件何时出现」的 binding 与 route。

## 6. 被否决

| 方案 | 理由 |
|---|---|
| 等 `turn/end` 事件再判定（不靠轮询） | 客户端未 retain 的会话拿不到事件；且会无限期等待 |
| 直接取消 Stop 的通知（靠 `pendingSubmissions` 或 cancel 信号） | 客户端拿不到 Stop 的显式信号，只能靠 `turn/end.reason` |
| 把 `unknown` 一律抑制 | 正常完成在事件迟到时会漏提示，不可接受 |
| 加长观察窗到 1 s | 治标；事件若真晚于 1 s 仍失效，且普遍拖慢提示 |

## 7. 测试要求

- R-12：binding 中只有陈旧 `completed`，`since` 之后出现 `aborted/user` → 重试后返回 `suppressed`。
- R-13：`since` 之后始终没有 `turn/end` → 预算耗尽返回 `completed`。
- R-14：慢路径返回陈旧 `at` → 重试；其后返回新 `at` → 采用新结果。
- R-15：`since - skew` 边界（±1 ms）判定正确。
- V12：真机 Stop 后**不弹**（复测）。
- 原 138 条不得回退。
